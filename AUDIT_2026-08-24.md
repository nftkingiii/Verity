# Verity competitive audit — 2026-08-24

## Verdict

Verity's Railway service is currently reachable and fast enough, but the ranking losses are primarily answer-quality and routing-contract problems rather than raw uptime problems.

1. `ONCHAIN_TX_LOOKUP` is returning `not_found` for valid Ethereum transactions because the production deployment still uses Cloudflare's public Ethereum RPC fallback. This is the largest and clearest defect.
2. `WEATHER_FORECAST` and `NEWS_SEARCH` have recently produced empty tournament answers. Their accepted input contracts are narrower than the questions now used by Telegraph, and both lack resilient stale-cache/fallback behavior.
3. `WEATHER_CHECK` is the closest miner to competitive: #3 is only 0.00194 behind #1 in epoch 269. Its main gaps are missing condition/location/dew-point/hourly context and a registry inconsistency.
4. The current evaluators are tied to Verity's private pipe-delimited canonical formats. Live miner traffic is heterogeneous JSON and natural language, so these evaluators cannot credibly beat the semantic champion scripts.
5. Track 2 is not currently covered. The live WASM registry shows only rejected registration #11 for the registered wallet; no active Verity scorer is visible.

## Implemented remediation — deployed and verified

- On-chain: archive-capable Ethereum default, ordered `RPC_ETHEREUM_URLS` support, independent fallback, reduced-confidence multi-provider `not_found`, and richer value/selector/gas/fee evidence. The exact failed epoch-269 transaction now resolves locally to the expected sender and `0.1049719 ETH`.
- Weather Check: place-name aliases, Open-Meteo geocoding, condition text, C/F temperature and dew point, pressure, provenance, and a direct natural-language answer.
- Forecast: place-name and `days` aliases, corrected numeric YAML types, local timezone, 1–7 daily forecasts, up to 168 hourly points, coverage metadata, and a mapped answer containing the hourly facts.
- News: `q`/`query`, `max` aliases, locale, recency, excluded-domain filters, descriptions, deterministic answer synthesis, and bounded stale-on-error caching.
- YAML: removed legacy endpoint-level `params` and `intents` fields that the current closed endpoint schema rejects; all four mapped labels now use `answer` while retaining canonical evidence.
- Scorers: expanded format-agnostic bounded scoring, realistic weather tolerances, partial per-field forecast scoring, and a new question-aware `NEWS_SEARCH` WASM.

## Miner audit

### 1. ONCHAIN_TX_LOOKUP — critical

The epoch-269 question asked for the sender and ETH value of a real Ethereum transaction. The ground truth identified the sender, recipient, value, block, and that it was a simple transfer. Verity returned:

```text
status: not_found
summary: The transaction was not found on the selected chain.
```

Chainsight, Truvian, and DegenLens all resolved it correctly. A direct 2026-08-24 probe confirmed that both `eth_getTransactionByHash` and `eth_getTransactionReceipt` return `null` for that transaction on `https://cloudflare-eth.com`. Verity therefore reproduced its configured upstream's false negative.

Required improvements, in order:

1. Configure a dedicated full-history Ethereum RPC in Railway immediately.
2. Add at least one independent fallback provider per chain.
3. Never treat a single provider's `null` as authoritative `not_found`; query the fallback and return `upstream_inconclusive` or reduced confidence when providers disagree.
4. Add `value_eth`, input selector/method classification, gas used, effective gas price, total fee, log count, and simple-transfer versus contract-call classification.
5. Add an `answer` or `signal` field that directly answers the question in natural language. Keep the compact canonical representation as evidence, not as the primary label.
6. Accept `hash`, `tx_hash`, `txHash`, and a natural-language `query` containing a transaction hash and chain alias.

The top miners' common advantage is not branding or endpoint count. It is a reliable RPC read plus a direct, number-first answer containing the exact facts the question asks for.

### 2. WEATHER_CHECK — recoverable

Epoch 269 placed Verity #3, very close to the top two. Verity returned the correct structural fields but omitted useful facts present in the question and leaders' responses:

- resolved city/country;
- human-readable condition;
- Fahrenheit values;
- dew point;
- pressure;
- source label;
- requested near-term hourly context.

Recommended update:

1. Convert Open-Meteo weather codes to condition text.
2. Add `temperature_f`, `apparent_temperature_f`, `dew_point_c`, `dew_point_f`, pressure, and source.
3. Return a direct summary such as: `Tokyo is 80.7°F (27.1°C), feels like 85.1°F, with a 72.5°F dew point.`
4. Accept `location`, `q`, or `query` in addition to coordinates; use only a fixed allowlisted geocoding host.
5. When requested, include a bounded next-24-hour hourly series instead of always returning current conditions only.

Registry issue: `verity-current-weather` appears in the epoch-269 leaderboard but is absent from both the Explorer integrations catalog and the official devnode miner catalog. That inconsistency can prevent routing even while historical scoring still displays the miner. Confirm the current registration ID/status with Telegraph before updating it.

### 3. WEATHER_FORECAST — critical contract/coverage gap

Verity's epoch-269 `miner_answer` was empty. The actual benchmark question requested a seven-day hourly forecast with Celsius temperature, precipitation probability, wind speed, a start date, and a delivery deadline. WeatherAPI was the only miner to return a large hourly payload and the only miner with a nonzero score.

Recommended update:

1. Accept `location`, `q`, and `query`, plus both `days` and `forecast_days` as integers.
2. Fix YAML type mismatches: endpoint parameters declare numbers/integers while `input_schema` currently declares coordinate and horizon values as strings.
3. Add up to 168 hourly records from Open-Meteo: temperature, dew point, precipitation probability, wind speed, and timestamp.
4. Preserve the daily summary, but make `summary` a real location-aware answer rather than a provenance sentence.
5. Parse requested start/end windows and return explicit coverage metadata when the request cannot be fully satisfied.
6. Add a stale-on-error cache and one retry within the response deadline.

### 4. NEWS_SEARCH — fix regression before changing provider

Verity historically ranked #1 for many broad news questions, then produced empty answers in 7 of its latest 20 scored rows, including epoch 268. GNews won that epoch by returning five articles with descriptions/content and structured country/language/count handling.

Recommended update:

1. Accept aliases `q`/`query` and `max`/`max_results` with consistent integer types.
2. Add optional `country`, `lang`, `category`, `from`, `to`, and excluded-domain inputs.
3. Translate constraints into Google News syntax such as `when:3d` and `-site:example.com`, then enforce filters again after parsing.
4. Parse usable RSS descriptions and return a short deterministic main-point summary per result.
5. Add retry plus stale-on-error caching. The current 30-second cache is discarded as soon as the upstream fails.
6. Log upstream status and duration without logging the full user query.
7. Only after the regression is fixed, compare Google News RSS against a keyed provider on the same held-out questions. A provider switch is not automatically better: GNews's epoch-268 winning score was still only 0.008731.

- All three have zero imports and are far below 32 MB: 7,594 B; 18,886 B; 19,720 B.

Structural validity is not competitiveness.

### Competitive defects

1. The on-chain scorer gives zero to any real answer that is not exactly Verity's seven-field pipe format. Live answers are JSON or prose, so it cannot rank current traffic.
2. The weather scorers only understand Verity's pipe formats. Their fallback is token Dice similarity for arbitrary text, which can reward verbose overlap without understanding numbers, units, dates, or JSON structure.
3. Weather Check requires exact timestamp and exact numeric equality. Correct sources often differ by observation minute, unit, and small measurement tolerances.
4. Forecast grants a day's entire weight only for an exact comma-delimited record. It cannot compare hourly forecasts or near-equivalent values from different sources.
5. None of the scorers uses the question to decide which facts matter.
6. There is no `NEWS_SEARCH` scorer.

### Required scorer redesign

Build format-agnostic, question-aware extractors rather than scorers for Verity's own serialization:

- On-chain: extract transaction hash, chain, addresses, status synonyms, block, value in wei/ETH, selector, fee, and simple-transfer/contract-call facts from JSON, prose, or pipe text. Weight only facts requested by the question.
- Weather Check: normalize °C/°F, compare temperatures and dew point with bounded tolerances, compare location/condition/time window, and penalize impossible values.
- Weather Forecast: align by date/hour, normalize units, score coverage separately from value accuracy, and give partial credit within defensible tolerances.
- News Search: score query relevance, requested count, recency window, country/category, excluded sources, source diversity, and whether each article includes a meaningful summary.

Use public historical score rows as a benchmark, but split them chronologically: development epochs first, latest epochs held out. Compare every candidate against the live champion binary and require:

- no traps, NaN, infinity, or out-of-range scores;
- empty answer exactly zero;
- worst self-match at least 0.75;
- benchmark score standard deviation above the platform floor;
- no regression in ordered good/bad cases;
- real-traffic rank agreement above 0.60, with a target above the current champion's observed agreement;
- bounded runtime on 128 KiB inputs.

## Update order

1. **On-chain infrastructure:** install a reliable Ethereum RPC plus fallback/quorum and prove the exact failed epoch-269 transaction now resolves correctly.
2. **Forecast contract:** accept location/query/day aliases and return bounded hourly data; remove recent empty answers.
3. **News reliability:** correct aliases/types, constraint parsing, retry, and stale-on-error cache; prove the epoch-268 question returns five filtered results.
4. **Weather Check enrichment and registry repair:** add condition/dew point/units/summary and resolve why the miner is missing from the active integrations catalog.
5. **Scorer rewrite:** start with `ONCHAIN_TX_LOOKUP`, benchmark against public traffic and the current champion, then Forecast, Weather Check, and News.
6. **Only then update Telegraph registrations.** Each miner update creates a new registration/intent ID, so prepare and verify the whole revision before signing.
